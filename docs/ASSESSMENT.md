# Phase 2 — Assessment

## Scope and evidence

This assessment is based on the Phase 1 source/test read-through, the committed 51-test baseline, the unchanged Phase 0 golden outputs, seven focused policy/audit tests, and the focused direct-executor runtime probe documented in [UNDERSTANDING.md](./UNDERSTANDING.md). Findings describe current behavior; they are not approvals to change code. In particular, the executor resource mismatch and unauthenticated demo-token route are not modified here. No files under `src/` or `tests/` were changed.

Risk scales: **High / Medium / Low** are qualitative. Blast radius names the paths or runtime surfaces affected. Security findings are ranked by severity and confidence; correctness findings by likely impact.

| COR-01 | `src/asg/policy.py:23-25` | When initialized with a rules list, `DeclarativePolicyEngine` retains the caller's mutable list rather than taking ownership or copying it. | A caller retaining that list can silently add, remove, or reorder active authorization rules without calling the engine API; an accidental mutation can change live decisions. No current production caller passes a pre-built list in `main.py`, so exploitability depends on future integrations. | Decide and document policy ownership, then isolate engine state or make the rule collection immutable at the boundary. | Medium: could change supported dynamic-update semantics. | Medium: policy decisions can change through untracked external mutation. | Policy engine construction and all evaluations using a supplied list. |
| COR-02 | `src/asg/executor.py:22-26` | `execute_tool` calls `args.get(...)` before checking that `args` is a dictionary. | A direct call with a non-dict argument raises an incidental `AttributeError` instead of the declared `ExecutorInputError`; the gateway currently validates first, so this is not an observed gateway bypass. | COR-03 | `src/asg/api.py:44`; `src/asg/gateway.py:32` | The HTTP request ID and gateway/audit request ID are independently generated for one request. | The returned `request_id` does not identify the audit records for that request, so operators cannot reliably correlate a client response with the audit trail. ## Security

| ID | file:line | problem (1 sentence) | why it matters (1–2 sentences) | suggested direction (1 sentence) | risk of fixing | risk of not fixing | blast radius |
|---|---|---|---|---|---|---|---|
| SEC-01 — Critical if reachable outside a trusted demo | `main.py:80-83`; `src/asg/idp.py:38-52`; `src/asg/auth.py:17-22` | The unauthenticated demo-token endpoint signs a caller-selected `principal_id` using the same process-local key and claims accepted by the protected execute endpoint. | Anyone able to reach this route can request a token for a configured privileged principal and then satisfy the execute route's JWT check; the route is therefore an identity-minting path, not merely a display/demo helper. Whether it is reachable in a real deployment is unknown, but it is mounted on the same app. | Remove it from production routing or restrict token issuance to an explicitly trusted demo boundary and non-privileged identities. | High: demo workflows and callers may rely on token issuance. | Critical: if exposed, arbitrary caller-selected identities can reach policy-approved data. | Authentication, principal identity, and every execute operation authorized by a minted token. |
| SEC-02 — High for direct executor exposure; confirmed local behavior | `src/asg/executor.py:22-37` | The executor validates the broker session against user-supplied `table_name` but chooses the actual SQL table independently from `tool_name`. | A runtime probe issued a token for `market_data` and directly called `read_client_pii` with `table_name="market_data"`; the executor returned the client PII fixture. This bypasses gateway registry and policy guards when a caller can reach the executor directly; the current HTTP path's registry validation prevents this mismatched pair, so remote reachability is not established. | Bind the validated session resource to the table selected for the tool and add a negative direct-executor regression test. | High: may break callers relying on the current mismatch or on direct execution assumptions. | High if another component or trust domain can invoke the executor; sensitive PII can be returned without policy evaluation. | Executor API, gateway-to-executor contract, and any direct in-process executor caller. |
| SEC-03 — Medium | `src/asg/gateway.py:86-99`; `src/asg/gateway.py:35-53` | `_log_audit` catches all exceptions without logging or surfacing them for validation and authorization decisions. | The request still fails closed for access when policy denies, but the audit record can silently disappear; during an audit outage, security decisions and validation failures become unobservable. This makes audit completeness impossible to infer from the caller-visible denial. | Preserve denial behavior while surfacing audit persistence failures through explicit logging/metrics or a clearly defined fail-closed policy. | Medium/High: changing error handling can alter denial responses or availability. | Medium/High: security-relevant denials may be absent from the durable trail with no signal. | All validation-denial and authorization-decision audit writes. |
| SEC-04 — Medium, threat-model dependent | `src/asg/audit_store.py:81-92` | `verify_integrity` recomputes each hash using its running prior digest but never checks the row's stored `previous_hash` value. | Altering only a stored `previous_hash` field is not detected, so the verifier's result does not establish that the persisted link metadata agrees with the recomputed chain. A writer able to rewrite the SQLite database can also recompute the unkeyed hashes, so this is not tamper evidence against a malicious database writer. | Define the audit threat model and verify all persisted chain-link fields; if hostile database rewriting is in scope, use an independently protected anchor or authentication mechanism. | Medium: changes integrity results and operational expectations for existing audit rows. | Medium: consumers may overestimate what `chain_intact` guarantees. | Audit integrity verification and any operator relying on its boolean result. |
| SEC-05 — Medium, concurrency dependent | `src/asg/audit_store.py:41-68` | Appending a record reads the last hash and inserts the next row in separate connections without serialization across the pair. | Concurrent writers can both observe the same predecessor and append divergent links; later sequential verification may reject the chain. No concurrency test currently establishes safety, and `check_same_thread=False` does not serialize this read/insert sequence. | Make predecessor selection and append atomic under the intended SQLite/process concurrency model, then add a concurrent append-and-verify test. | Medium: locking or transaction changes can affect throughput and ordering. | Medium: concurrent traffic can compromise chain continuity and audit verification. | Persistent audit writes in single- or multi-threaded/multi-worker deployments. |
| SEC-06 — Low/Medium, deployment dependent | `src/asg/api.py:29-37`; `main.py:85-88` | Tool discovery, audit-record retrieval, and audit-integrity status are exposed without an authentication dependency. | Audit records reveal principal, resource, tool, outcome, and reason metadata, while integrity status can aid reconnaissance; no row data is returned by these endpoints. Whether this violates the intended deployment boundary is unknown. | Decide which operational endpoints are public and apply a documented authorization boundary to those that are not. | Low/Medium: may affect consoles, demos, or monitoring clients. | Low/Medium: exposes operational/security metadata to any reachable caller. | Tool catalog and audit-read/integrity routes. |
| SEC-07 — Low, assurance clarity | `src/asg/broker.py:19-39` | The broker computes and stores a per-session `hash`, but validation never reads or verifies it. | The field can imply an integrity check that does not occur; token validity actually depends on dictionary membership, expiry, and resource equality. No bypass was demonstrated from the unused field alone. | Remove the unused assurance signal or define and test the invariant it is meant to enforce. | Low: alters an internal session shape and any introspection using it. | Low: maintainers may incorrectly rely on a non-enforced integrity property. | Broker session representation and broker validation expectations. |

## Unknowns

- **Deployment exposure:** It is not known whether `main.py`'s app or the demo-token endpoint is exposed beyond a local prototype, whether an ingress proxy restricts routes, or whether the app runs behind an authentication layer not present in the repository. SEC-01's severity depends materially on this.
- **Executor reachability:** The direct executor mismatch is confirmed through an in-process call, but no deployment topology or plugin architecture establishes whether an untrusted component can call `ControlledToolExecutor` directly. The HTTP gateway configuration observed in `main.py` does not produce the mismatched tool/resource pair because registry validation rejects it.
- **Secret usage:** The source-literal service secret is present, but its actual deployment use, rotation history, repository visibility, and whether it is intentionally a non-secret local placeholder are unknown. No credential scanning or external deployment inspection was performed.
- **Demo identity intent:** The intended allowed principals for `/api/v1/auth/demo-token` are undocumented. It is not known whether it is explicitly enabled only in a local/demo environment or whether arbitrary principal selection is expected behavior for a prototype.
- **Identity provider lifecycle:** The intended signing key persistence, rotation, revocation, key identifier policy, and multi-worker behavior are unspecified. The observed process-local key is consistent with a toy IdP but not with a stable external identity service.
- **Audit threat model:** It is unknown whether the hash chain is intended to catch accidental corruption, deter application-level edits, support compliance evidence, or resist a hostile host/database administrator. The appropriate remedy for an unkeyed, locally stored chain depends on that threat model.
- **Concurrency and deployment scale:** No worker count, threadpool configuration, request rate, connection lifecycle, or multi-process deployment target is present. Audit append races and synchronous endpoint blocking are structurally plausible but have not been reproduced under concurrent production load.
- **Data sensitivity and authorization policy:** Client PII is represented by a fixture, but real data classification, principal provisioning, ownership/assignment semantics, and policy administration controls are not supplied. It is unknown whether the current static policy is only illustrative or intended to represent real authorization.
- **Audit retention and privacy:** Retention, deletion, backup, access control on `audit.db`, and whether principal/resource/reason metadata is itself sensitive are unspecified. No policy for exposing `/api/v1/audit` is documented.
- **Error/telemetry requirements:** There is no logging, metrics, tracing, alerting, or service-level objective specification in the reviewed materials. It is unknown whether audit failures are intentionally swallowed to preserve availability or whether this is accidental.
- **Uncollected tests:** `tests/deck.py` appears to contain test functions but is not part of the 51-test baseline. It is unknown whether it is intentionally an investor demo/deck artifact, an abandoned test suite, or expected CI coverage.
- **Runner support:** `run_phase5.py` is out of sync with current APIs, but its intended audience and whether it must remain runnable are unknown. It was not executed.
- **Dependency ownership:** `pyproject.toml` does not directly declare the JWT or cryptography imports found in source. It is unknown whether they are intentionally transitive, provided by a separate environment lock/installer, or omitted from the manifest.
- **Python/static analysis policy:** No mypy configuration, type-check workflow, or required strictness level was found in the reviewed setup. It is unknown whether the team values a gradual security-boundary typing approach or enforces a separate type-check job.
- **API compatibility expectations:** The Phase 0 OpenAPI and golden snapshots are committed, but no client inventory, versioning policy, or deprecation policy establishes whether identifiers, status/error details, or unauthenticated discovery routes have external consumers.
- **Operational database scope:** The app uses a mock in-memory data database and a local SQLite audit database. No evidence establishes the intended production database, transaction guarantees, migrations, backup plan, or whether multiple processes share one audit file.
- **No independent system review:** This assessment is based on the requested repository files and local tests. It does not include infrastructure-as-code, deployment manifests, external services, production logs, dependency vulnerability scanning, or a full threat model; those may change risk ratings and implementation direction.
